# Whauto AI — Instructions Claude Code

## Contexte projet

Whauto AI est un SaaS de commerce conversationnel exclusivement centré sur WhatsApp Business (Cloud API officielle Meta — jamais WhatsApp Web, scraping, ou session QR non officielle).

Un commerçant connecte son numéro WhatsApp Business à la plateforme, qui centralise conversations, agent IA, reprise humaine, contacts, catalogue, panier conversationnel, commandes, paiements, livraisons et statistiques. L'IA qualifie le besoin client et recommande des produits, mais n'est **jamais** source de vérité pour les prix, stocks, commandes ou paiements — ces données viennent toujours de services métier déterministes et de la base de données, jamais du LLM directement.

Ce projet a été entièrement redémarré le 2026-07-11 (code V1 supprimé). Le présent document reflète uniquement les fondations techniques validées ; il sera complété module par module.

## Méthode de travail

Avancer module par module, jamais tout générer en une fois. Avant chaque implémentation importante : analyser le besoin, proposer les choix techniques, signaler risques/dépendances, présenter les fichiers concernés, attendre validation si plusieurs choix structurants sont possibles. Ne jamais créer de faux service prétendument fonctionnel — toute intégration externe non disponible est isolée derrière une interface avec une implémentation Mock explicitement nommée. Ne jamais modifier un fichier sans avoir vérifié son contenu actuel.

## Architecture multi-tenant (implémentée)

Entité racine : `Organization` (statuts ACTIVE/SUSPENDED/ARCHIVED). Un `User` y est lié par `Membership` (rôle OWNER/ADMIN/MANAGER/AGENT, statut ACTIVE/SUSPENDED/LEFT, unique par user+org). Le Membership vérifié en base est **la seule** source de vérité d'accès au tenant.

**Chaîne de gardes** sur toute route tenant-scopée : `JwtAuthGuard → [EmailVerifiedGuard] → TenantGuard → PermissionsGuard`. `TenantGuard` (`apps/api/src/common/tenant/`) résout l'organisation depuis le path param `:organizationId` ou le header `X-Organization-Id` (les deux présents et différents → 400), vérifie le Membership ACTIVE + le statut de l'org (SUSPENDED bloque tout ; ARCHIVED bloque tout sauf routes `@AllowArchived`), puis attache `request.tenant = { userId, organizationId, membershipId, role, permissions }`. Un non-membre reçoit **404** (anti-énumération), jamais 403.

**RBAC** : source unique `common/tenant/permissions.ts` (matrice `ROLE_PERMISSIONS`, poids `ROLE_WEIGHT`). Hiérarchie stricte : on n'agit/n'assigne que des rôles **strictement inférieurs** au sien (OWNER intouchable via routes standards ; un ADMIN ne gère pas un ADMIN). `@RequirePermissions(...)` + `PermissionsGuard`. Jamais de rôle lu depuis le frontend.

**Règles pour tout futur modèle métier (Shops, Products, Conversations…) :**
- colonne `organizationId` obligatoire + index ;
- jamais de `findUnique({ id })` seul sur une donnée tenant-scopée — toujours `organizationId` dans le filtre (`findFirst({ where: { id, organizationId: tenant.organizationId } })`) ;
- jamais d'`organizationId` accepté depuis le body quand il dérive du TenantContext ;
- écritures conditionnelles (`updateMany` + vérification de `count`) pour les transitions d'état concurrentes ;
- l'extension Prisma d'injection automatique a été volontairement reportée (décision 2026-07-12) — à réévaluer avec Products/Conversations/Orders.

**Index uniques partiels en SQL brut** (inexprimables dans `schema.prisma`) : une seule invitation PENDING par (org, email) et un seul Membership OWNER ACTIVE par org (migration `20260712212611_organizations_module`) ; une seule Shop principale non archivée par org (`shops_one_primary_per_org`, migration `20260712221706_shops_module`) ; un seul canal WhatsApp actif (CONNECTING/CONNECTED/SUSPENDED) par Shop (`whatsapp_channels_one_active_per_shop`) et une seule conversation OPEN/PENDING par (channel, contact) (`conversations_one_active_per_contact_channel`), migration `20260717090000_whatsapp_conversations_module` ; catalogue (migration `20260718080000_products_catalog_module`) : nom de catégorie unique par Shop insensible à la casse (`product_categories_unique_name_ci_per_shop`), une variante DEFAULT non archivée par produit, une combinaison vivante unique par produit (`product_variants_unique_combination_per_product`), une image principale par produit — plus des CHECK SQL (prix ≥ 0, compareAt > prix, stock jamais négatif). ⚠️ `prisma db push` ne les recrée pas — toujours passer par les migrations ; le seed échoue s'ils manquent. ⚠️ Le P2002 d'un index partiel brut remonte `meta.target` = colonnes de l'index (ex. `["organizationId"]`), pas son nom — vérifié sur Prisma 6.19.

**Convention PATCH (validée, s'applique à tous les modules)** : dans un DTO de modification, `undefined` (champ absent) = inchangé ; `null` = effacement, autorisé uniquement sur les champs optionnels (`@IsOptional` accepte null) ; les champs requis utilisent `@ValidateIf((_, v) => v !== undefined)` et refusent null. Les champs pilotés par des routes dédiées (`status`, `isPrimary`…) ne sont jamais acceptés dans un PATCH.

**Cascades de suppression** : `Organization → Shop → ShopOpeningHour` (et memberships/invitations/audit) sont en `onDelete: Cascade`. Aucun mécanisme de suppression physique d'Organization n'existe côté API (archivage logique uniquement) — la cascade ne joue qu'en test/dev via Prisma direct.

## Conventions de code

- TypeScript strict partout, pas de `any` non justifié.
- Controllers NestJS fins, toute la logique dans les services.
- Accès Prisma tenant-scopé centralisé dans des repositories par agrégat.
- Erreurs métier via des classes dédiées (`DomainError` et sous-classes dans `@whauto/shared`), mappées par un filtre d'exception global — jamais de fuite de détails internes.
- Montants toujours en entier (plus petite unité monétaire) — jamais de flottant JS pour l'argent.
- `correlationId` propagé sur chaque requête et présent dans les logs structurés (pino).
- Aucune logique métier dans les composants React ; TanStack Query pour tout l'état serveur (query keys par feature, scoppées par `organizationId`).
- Un module NestJS = un dossier avec `*.module.ts`, `*.controller.ts`, `*.service.ts`, `dto/`, tests colocalisés.
- Tests : Jest pour `apps/api` et `apps/whatsapp-worker` ; Vitest pour `apps/web` et les packages purs.

## Sécurité — règles absolues

- Ne jamais committer `.env`.
- JWT : access token 15 min, refresh token 7 jours, rotation à chaque refresh, stocké côté client en cookie `httpOnly` + `SameSite=Strict` (jamais `localStorage`).
- Vérification HMAC-SHA256 obligatoire sur tout webhook Meta avant traitement (à implémenter avec le module WhatsApp).
- Isolation multi-tenant systématique — jamais de requête cross-tenant.
- Secrets (tokens Meta, clés paiement) chiffrés au repos, jamais loggés, jamais en clair dans un job BullMQ.
- Idempotence obligatoire sur les webhooks (WhatsApp et paiement) et sur les envois sortants.

## Module Auth (implémenté)

- **Mots de passe** : Argon2id via `@node-rs/argon2`, encapsulé exclusivement dans `PasswordService` (seul fichier autorisé à l'importer).
- **Access token** : JWT 15 min (`JwtService`), retourné dans le JSON — le client le garde en mémoire, jamais en `localStorage`.
- **Refresh token** : opaque 256 bits, stocké hashé (SHA-256), cookie `HttpOnly` `SameSite=Strict` `Path=/api/auth`, host-only (pas de `COOKIE_DOMAIN` par défaut). Rotation atomique à chaque refresh : `updateMany` conditionnel (`revokedAt=null`, `expiresAt>now`, count===1) dans une transaction — deux refresh concurrents ne réussissent jamais tous les deux ; la réutilisation d'un token consommé révoque toute la famille de sessions.
- **Statuts** : un compte naît `PENDING_VERIFICATION` et peut se connecter (accès à `me`, `refresh`, `resend-verification`, `logout`). `EmailVerifiedGuard` est prêt (`apps/api/src/modules/auth/email-verified.guard.ts`) mais **pas encore appliqué** — les futurs modules métier le poseront après `JwtAuthGuard`.
- **Anti-énumération** : `login` et `forgot-password` répondent de façon générique ; `register` renvoie 409 `EMAIL_ALREADY_USED` seulement pour un compte déjà actif (un compte PENDING reçoit une réponse générique + renvoi de vérification).
- **Email** : aucune intégration réelle — interface `EmailProvider` + `ConsoleEmailProvider` (mock explicite). Liens de vérification/reset exposés dans la réponse HTTP uniquement si `NODE_ENV=development` **et** `AUTH_EXPOSE_TEST_TOKENS=true`.
- **Rate limiting** : Redis via `@nest-lab/throttler-storage-redis@1.2.0` (compatibilité vérifiée 2026-07-12 : peers NestJS ^11, throttler >=6, ioredis >=5). Limites par endpoint en paires `AUTH_RATE_LIMIT_*_MAX` / `AUTH_RATE_LIMIT_*_WINDOW_SECONDS`, validées par Zod.
- **change-password** : vérifie le mot de passe courant, révoque toutes les sessions (y compris la courante) et en recrée une, le tout transactionnel ; nouveaux access + refresh tokens émis.
- **Nettoyage** : `AuthCleanupService.cleanupExpired()` (sessions et tokens périmés) — sans planificateur pour l'instant, réutilisable par le worker.
- **Sorties API** : selects Prisma explicites (`USER_PUBLIC_SELECT`) + DTO/mappers — `passwordHash`/`tokenHash` ne sont jamais chargés hors besoin, jamais sérialisés.
- **Erreurs** : `DomainError` mappée par `DomainErrorFilter` global (`statusCode`, `code`, `message` — rien d'autre).

## Module Organizations (implémenté)

- **Création** : `POST /organizations` (email vérifié requis) — Organization + Membership OWNER + audit `ORGANIZATION_CREATED` dans une transaction. Slug généré depuis le nom (retry suffixé en cas de collision) ou fourni (409 si pris). Défauts : timezone `Africa/Douala`, devise `XAF`, locale `fr` (validés `@IsTimeZone`/`@IsISO4217CurrencyCode`/`@IsLocale`).
- **OWNER unique** : pas de transfert dans cette phase ; garanti par l'index partiel PostgreSQL, pas seulement par le code.
- **Invitations** : modèle `OrganizationInvitation`, enum `InvitationRole` (ADMIN/MANAGER/AGENT — la base ne peut pas stocker une invitation OWNER), token opaque 256 bits stocké hashé (SHA-256), expiration `INVITATION_EXPIRES_IN_DAYS` (7 j) **fonctionnelle dès `expiresAt < now()`** avec transition paresseuse vers EXPIRED. Réinviter un email avec une PENDING existante **renouvelle la même ligne** (nouveau tokenHash — l'ancien lien meurt — nouveau expiresAt, audit `INVITATION_RESENT`). Acceptation : email du compte = email invité, consommation `updateMany` conditionnelle en transaction avec création (ou réactivation d'un Membership LEFT — jamais SUSPENDED) + audit `INVITATION_ACCEPTED`.
- **Membres** : liste paginée (`page`/`limit`, défauts 1/20, max 100, réponse `{ items, total, page, limit }`), changement de rôle et retrait avec hiérarchie stricte et écritures conditionnelles ; retrait/départ → Membership `LEFT` conservé (audit + réactivation). L'OWNER ne peut pas quitter.
- **Archivage** : `POST /:organizationId/archive` (OWNER), logique uniquement, `updateMany` conditionnel ; ensuite lecture seule via `@AllowArchived` sur `GET /:organizationId`, tout le reste 403.
- **Audit** : modèle `OrganizationAuditEvent` séparé d'`AuthAuditEvent`. Les événements structurants (`ORGANIZATION_CREATED/ARCHIVED`, `INVITATION_ACCEPTED`, `MEMBER_ROLE_CHANGED/REMOVED/LEFT`) s'écrivent dans la même transaction que l'action ; les secondaires via `recordSafe` (non bloquant). Jamais de token/secret en metadata.

## Module Shops (implémenté)

- **Modèle** : `Shop` (statuts DRAFT/ACTIVE/INACTIVE/ARCHIVED — pas de SUSPENDED, réservé au niveau plateforme/Organization), slug unique **par organisation** (`@@unique([organizationId, slug])`), adresse et politiques (2000 car. max) inline, `BusinessType` enum nullable avec OTHER, lat/long Float optionnels. `countryCode` requis à la création, jamais déduit de la devise ; timezone/currency/locale hérités de l'Organization si absents. Validation régionale par class-validator 0.14.4 (`@IsTimeZone`, `@IsISO4217CurrencyCode`, `@IsISO31661Alpha2` — compatibilité vérifiée).
- **Shop principale** : au plus une par org, non archivée — garantie par l'index partiel PostgreSQL. Première Shop créée = principale (retry `isPrimary=false` uniquement sur le conflit de l'index primaire, jamais sur une collision de slug). `set-primary` transactionnel, idempotent, retries ciblés (P2002 primaire, P2034 write conflict). Archivage d'une principale → promotion déterministe : plus ancienne ACTIVE, sinon INACTIVE, sinon DRAFT (ordre secondaire par id), sinon aucune.
- **Transitions** : DRAFT→ACTIVE|ARCHIVED, ACTIVE→INACTIVE|ARCHIVED, INACTIVE→ACTIVE|ARCHIVED ; ARCHIVED terminal (lecture seule, exclue des listes par défaut, `includeArchived=true` pour les voir). Activation soumise aux champs minimums (name, countryCode, timezone, currency, locale). `updateMany` conditionnels partout.
- **Horaires** : `ShopOpeningHour` = une ligne par plage (multi-plages par jour), minutes depuis minuit en base / "HH:mm" dans l'API, jour fermé = zéro ligne, pas de plage traversant minuit. `PUT` = remplacement complet transactionnel (deleteMany + createMany + audit dans la même transaction).
- **Permissions** : `shops.read` (tous les rôles), `shops.update`/`shops.manageSettings` (+MANAGER), `shops.create`/`shops.activate` (couvre activate/deactivate/set-primary)/`shops.archive` (OWNER/ADMIN).
- **Audit** : extension d'`OrganizationAuditEventType` (7 événements SHOP_*), tous écrits dans la transaction métier — y compris SHOP_UPDATED (metadata = noms des champs modifiés, jamais le contenu) et SHOP_OPENING_HOURS_UPDATED (metadata synthétique) : un échec d'audit annule l'action.
- **Recherche** : name/slug `contains` insensible à la casse, toujours dans le `where` tenant-scopé.

## Module Meta Cloud API (implémenté — sous-phase A : Meta sans IA)

- **Provider** : `MetaCloudWhatsAppProvider` (`packages/whatsapp`, TS pur — config INJECTÉE, jamais de `process.env` dans le package). Implémente le contrat `WhatsAppProvider` existant ; le mock reste disponible (la factory choisit par `channel.provider`). `validateInboundEvent` = HMAC-SHA256 du corps BRUT (timing-safe) — **autorité cryptographique unique** ; `parseInboundEvent` = `entry[].changes[].value.{messages,statuses}` (un webhook porte plusieurs événements), défensif (type inconnu → UNSUPPORTED, jamais d'exception) ; `sendTextMessage` = POST Graph ; `mapMetaError` classifie (RETRYABLE / NON_RETRYABLE / REQUIRES_TEMPLATE / CONFIGURATION_ERROR) ; `validateConfiguration` = GET Graph (health, **aucun envoi**). **`META_GRAPH_API_BASE_URL` configurable** : les tests pointent un faux serveur Graph local et exercent le VRAI provider (URL, en-têtes Bearer, payload, timeout, mapping d'erreurs) sans jamais appeler Meta.
- **Secrets EN ENVIRONNEMENT UNIQUEMENT** (validé) : `META_APP_SECRET`/`META_ACCESS_TOKEN`/`META_WEBHOOK_VERIFY_TOKEN` jamais en base, log, Swagger, test ou frontend ; les colonnes `*Encrypted` du channel restent nulles cette phase (pas de module de chiffrement). `.env.example` ne contient QUE des valeurs vides/factices. Config pilote unique (une Shop de test liée au `META_PHONE_NUMBER_ID` de l'env) ; ni Embedded Signup ni multi-tokens.
- **Raw body** : `NestFactory.create(AppModule, { rawBody: true })` — additif, ne casse pas le parsing JSON (testé par non-régression). Le HMAC utilise `req.rawBody` (jamais le JSON re-sérialisé).
- **Webhook** (`WebhooksModule`, PUBLIC — aucun guard tenant) : `GET /api/webhooks/whatsapp/meta` (vérification `hub.verify_token` timing-safe → challenge, sinon 403, token jamais loggé) ; `POST /api/webhooks/whatsapp/meta` (contrôleur ultra-fin : passe rawBody + signature + body au service → provider vérifie le HMAC UNE fois → parse → résout le Channel par `phone_number_id` → **durable inbox** existante → ACK 200 rapide). Signature invalide/absente → 401. **`phone_number_id` inconnu avec signature valide → ACK 200, log technique filtré, AUCUNE écriture métier** (validé). Aucun appel lourd/IA avant l'ACK.
- **Types de message entrants** : le VRAI type est conservé (`MessageType` étendu : STICKER, UNSUPPORTED ; CONTACTS→CONTACT). Les médias sont stockés avec leur type et `textContent=null` — jamais convertis en texte (l'UI génère le libellé « non pris en charge »). Seul TEXT est « supporté » (déclenchera l'IA en sous-phase B).
- **Outbound** : réutilise le flux existant (Message PENDING + OutboxEvent + dispatchId → worker → `provider.sendTextMessage`). La factory worker construit le provider Meta depuis l'env. Le processor outbound respecte la **classe d'erreur** : une erreur DÉFINITIVE (NON_RETRYABLE/CONFIGURATION_ERROR/REQUIRES_TEMPLATE) → FAILED immédiat, jamais de retry en boucle.
- **Statuts** : mapping Meta `delivered/read/failed` → transitions monotones existantes (`sent` non traité comme entrant). **Statut orphelin** (providerMessageId encore inconnu, validé) : `MessageStatusService.apply` renvoie `messageFound=false` (jamais throw) → l'événement passe `WAITING_MESSAGE` (nouvel état, **jamais FAILED**) ; le sweep le réconcilie (Message retrouvé → PROCESSED) ou le passe `ORPHANED` après `WHATSAPP_ORPHAN_STATUS_TTL_MS` (terminal). `FAILED` reste réservé aux vraies erreurs techniques.
- **Endpoints channel Meta** (`whatsapp-channel/meta/*`, permission `whatsappChannels.manage`) : `connect` (config env, vérifiée via Graph GET, aucun envoi, un seul canal actif par Shop) ; `health` (GET Graph, **JAMAIS d'envoi**, ne renvoie aucun secret, ok:false + audit `META_CHANNEL_ERROR` en cas d'échec) ; `send-test` (envoi RÉEL de diagnostic, `confirm=true` OBLIGATOIRE, distinct du flux conversationnel, ne renvoie que le providerMessageId). Audit : `META_CHANNEL_CONNECTED/TESTED/ERROR`.
- **Tests** : unitaires provider (`packages/whatsapp/src/meta-provider.test.ts` — HMAC valide/invalide/absent/longueur, corps brut vs re-sérialisé, parsers text/média/statuts/inconnu, mapping d'erreurs, jamais de fuite de secret) ; e2e `test/meta-whatsapp.e2e-spec.ts` (20 scénarios avec **faux serveur Graph** exerçant le vrai provider + worker réel : verify GET, HMAC 401, inbound texte/média/dédup, phone_number_id inconnu → ACK sans écriture, outbound → SENT → DELIVERED → READ, erreur Meta → FAILED, orphelin réconcilié + ORPHANED, health sans envoi, send-test confirm=true, isolation, non-régression rawBody + mock inchangé). ⚠️ Jest CJS n'autorise pas `import()` dynamique : le faux Graph écoute sur un **port fixe** connu avant l'import statique d'AppModule.
- **Sous-phases B (Gemini SUGGEST_ONLY) et C (AUTO_REPLY) : NON commencées** — à valider après le test Meta réel externe documenté.

## Module WhatsApp conversationnel (implémenté — provider MOCK)

- **Modèles** : `WhatsAppChannel` (provider MOCK/META_CLOUD, statuts DISCONNECTED/CONNECTING/CONNECTED/ERROR/SUSPENDED), `Contact` (unique par `(shopId, normalizedPhone)` E.164 — même numéro possible dans deux Shops), `Conversation` (OPEN/PENDING/RESOLVED/CLOSED, mode HUMAN par défaut — AI/HYBRID réservés, priorité, `assignedMembershipId`, `unreadCount`, `customerServiceWindowExpiresAt`), `Message` (directions INBOUND/OUTBOUND/INTERNAL ; seuls TEXT/SYSTEM/INTERNAL_NOTE sont réellement fonctionnels), `Tag` + `ConversationTag` (tenant-scopés, unique par (org, name), upsert à l'ajout).
- **Cohérence Channel↔Shop↔Org garantie EN BASE** : FK composite `(shopId, organizationId)` → `shops(id, organizationId)` — une écriture SQL directe cross-tenant est refusée (testé e2e).
- **Canal** : un seul actif par Shop (index partiel — ERROR n'occupe PAS le slot : un canal en erreur est remplaçable par une nouvelle connexion, qui le clôt dans la même transaction ; historique conservé). Seul MOCK se connecte dans cette phase ; META_CLOUD lève `WHATSAPP_PROVIDER_NOT_IMPLEMENTED` (501). Aucun secret Meta nulle part.
- **Durable inbox (`WhatsAppInboundEvent`)** : tout événement fournisseur validé est persisté (unique `(channelId, externalEventId)`, statuts RECEIVED/QUEUED/PROCESSING/PROCESSED/FAILED) AVANT l'ACK HTTP et AVANT toute publication BullMQ — Redis n'est jamais la seule trace. Payload = événement normalisé, jamais de signature/token/header.
- **Transactional outbox (`OutboxEvent`)** : le Message OUTBOUND PENDING, la mise à jour de la Conversation et l'OutboxEvent `WHATSAPP_MESSAGE_SEND_REQUESTED` sont créés dans la MÊME transaction ; publication BullMQ post-commit best-effort.
- **Récupération (worker `RecoveryService`)** : sweep périodique (`WHATSAPP_RECOVERY_*`) — inbound RECEIVED/QUEUED/PROCESSING périmés et FAILED sous plafond de tentatives republiés ; outbox PENDING republiés avec `jobId = dispatchId` (jamais de double envoi logique). Reprise garantie après crash API/worker/Redis (testé e2e).
- **Queues BullMQ** (noms = constantes `WHATSAPP_QUEUES` de `@whauto/shared`, JAMAIS des variables d'env) : `whatsapp-inbound` (jobId = inboundEventId), `whatsapp-outbound` (jobId = dispatchId), `whatsapp-status` (statuts SIMULÉS mock, jobs différés). Connexions Redis DÉDIÉES `maxRetriesPerRequest: null` (jamais le client rate-limiting). `removeOnFail: false` = dead-letter naturelle. ⚠️ **BullMQ interdit `:` dans le jobId d'un job DIFFÉRÉ** (« Custom Id cannot contain : ») — séparateur `.` obligatoire (bug réel corrigé, silencieux : l'add échoue mais le job appelant réussit au retry).
- **Worker (`apps/whatsapp-worker`)** : processors inbound (claim conditionnel RECEIVED/QUEUED/FAILED→PROCESSING, transaction Contact upsert + Conversation active-ou-créée + Message + compteurs), outbound (PENDING→QUEUED→SENT ; **un retry BullMQ sur un message déjà QUEUED CONTINUE l'envoi** ; SENT/DELIVERED/READ = job déjà traité ; FAILED uniquement via retry explicite ; `dispatchId`/`attemptCount`/`lastAttemptAt` tracent chaque tentative), status (transitions conditionnelles).
- **Transitions Message** : source unique `@whauto/shared` (`statusesUpgradableTo`/`statusesFailableFrom`/`isStatusUpgrade`), partagée API/worker/frontend. PENDING→QUEUED→SENT→DELIVERED→READ ; READ out-of-order backfille `deliveredAt` ; jamais de rétrogradation ; SENT→FAILED seulement sur événement fournisseur explicite ; FAILED→PENDING seulement via `POST …/messages/:id/retry` (nouveau dispatchId). ⚠️ Risque documenté : envoi provider réussi + réponse réseau perdue = renvoi possible (Meta ne fournit aucune idempotence externe dans cette phase).
- **Fenêtre 24 h** : `computeCustomerServiceWindowExpiry` (`@whauto/shared`) — basée sur le timestamp PROVIDER, max(courante, candidate) : un événement ancien ne réduit jamais la fenêtre ; timestamp futur borné à now. Vérifiée à l'API (422 `CUSTOMER_SERVICE_WINDOW_EXPIRED`) ET au worker (autorité finale, FAILED déterministe). Notes internes jamais soumises.
- **Conversations** : une seule active par (channel, contact) — index partiel + retry P2002. RESOLVED/CLOSED ne sont JAMAIS rouvertes par un inbound (nouvelle conversation OPEN). RESOLVED→OPEN manuelle possible (protégée par l'index) ; CLOSED terminal. Répondre exige OPEN/PENDING.

## Module Panier conversationnel (implémenté — Cart + Réservations de stock + Checkout Foundation)

- **Modèles** : `Cart` (5 statuts ACTIVE/CHECKOUT_STARTED/CONVERTED/ABANDONED/EXPIRED — table `CART_TRANSITIONS` dans `@whauto/shared` ; totaux stockés recalculés serveur à chaque mutation ; `version` verrou optimiste ; `lastActivityAt`/`expiresAt` inactivité), `CartItem` (snapshots produit/variante/prix au moment de l'ajout + `availabilityStatus`/`currentPriceMinor` de revalidation, `@@unique([cartId, variantId])` — même variante = incrément), `StockReservation` (**historique** : plusieurs lignes par CartItem, une seule ACTIVE garantie par index partiel `stock_reservations_one_active_per_cart_item` ; chaque cycle crée une NOUVELLE ligne, jamais de réutilisation ; `renewedCount`/`lastRenewedAt`/`maxExpiresAt` plafond de vie cumulée), `CheckoutSession` (1:1 Cart, `confirmationSnapshot` Json immuable = livrable pour la future conversion en Order), `CartMutation` (idempotence `@@unique([conversationId, clientMutationId])`, purge 24 h par le worker). FK composites chaînées vers shops/contacts/conversations/products/variants (cohérence cross-tenant EN BASE, testée par SQL direct) + CHECK SQL (totaux ≥ 0, quantités > 0, `lineSubtotal = unitPrice × quantity`).
- **Réservations** : uniquement pendant le checkout (start = TOUT-OU-RIEN : verrou `FOR UPDATE` sur le Cart → revalidation en transaction → réservation atomique de chaque ligne suivie → CheckoutSession → transition → audits ; un échec annule tout). Réservation atomique = `UPDATE inventory_items … FROM product_variants WHERE (allowBackorder OR onHand − reserved ≥ q) RETURNING` — compteurs before/after exacts, zéro read-then-write. Changement de quantité pendant checkout : seule la **différence** est réservée/libérée (même transaction). Release idempotent : transition conditionnelle ACTIVE→terminal qui GATE le décrément (count=0 = no-op, jamais de double décrément). Renouvellement throttlé (`STOCK_RESERVATION_RENEWAL_MIN_INTERVAL_SECONDS`) sur action significative, plafonné à `maxExpiresAt` — jamais indéfini.
- **`InventoryMovement` étendu** : types RESERVATION/RELEASE avec `quantityDelta=0`, `quantityBefore=quantityAfter` (onHand INCHANGÉ) et `quantityReservedBefore/After` remplis — sémantique verrouillée par CHECK SQL (`inventory_movements_reservation_semantics` + colonnes appariées). `quantityBefore/After` gardent leur sens onHand pour tous les types existants.
- **Concurrence** : `expectedVersion` requis sur les mutations (Cart et Checkout) → 409 `CART_CONCURRENCY`, l'UI recharge et fait réessayer. `clientMutationId` (chaîne 8-64 caractères, PAS un format UUID imposé) sur add/update/start/confirm/abandon : rejouer la même mutation renvoie l'état courant SANS double effet (insert `CartMutation` dans la transaction, P2002 → replay détecté). Deux checkouts concurrents sur le dernier article : un seul gagne (`STOCK_RESERVATION_FAILED` pour l'autre), vérifié e2e par `Promise.all`.
- **Revalidation** (`revalidateCartLine` dans `@whauto/shared`, priorités PRODUCT_UNAVAILABLE > VARIANT_UNAVAILABLE > PRICE_CHANGED > stock) : JAMAIS de correction silencieuse — un prix modifié reste `PRICE_CHANGED` jusqu'à `accept-current-price` explicite ; le stock exclut la réservation de la propre ligne (`reservedByThisLine`). Revalidation au GET, avant résumé, au start et au confirm.
- **Checkout** : `PATCH` collecte (PICKUP : nom+téléphone ; DELIVERY : + ville + (adresse OU repère) + pays — `missingCheckoutFields` partagé, statut dérivé `READY_FOR_CONFIRMATION`), `customerPhone` prérempli du Contact. **Confirm atomique** : verrou des deux entités, versions vérifiées, revalidation complète, réservations ACTIVE non expirées exigées (expirée pendant l'opération → refus testé), totaux recalculés serveur, snapshot construit CÔTÉ SERVEUR (lignes/totaux/client/adresse/réservations), transition conditionnelle → CONFIRMED. Après CONFIRMED : panier et checkout IMMUABLES (`CHECKOUT_ALREADY_CONFIRMED`), réservations conservées jusqu'à conversion ou expiration. Cancel : release complet + session CANCELLED + Cart → ACTIVE. Aucun Order définitif dans cette phase — le snapshot est le livrable.
- **Worker (sweep `CART_EXPIRATION_SWEEP_INTERVAL_SECONDS`)** : réservations expirées (release + Cart → ACTIVE quand plus aucune ACTIVE, checkout et données conservés), paniers inactifs (`CART_INACTIVITY_TTL_MINUTES`, jamais un checkout CONFIRMED) → EXPIRED + release + session EXPIRED + audit `CART_EXPIRED`, orphelins, purge `CartMutation` ; claims conditionnels idempotents, événements temps réel via `RealtimeEmitterService`.
- **Résumé conversationnel** : `GET summary-text` revalide puis génère le texte serveur (`buildCartSummaryText` — « Livraison : à définir » tant que non choisie) + `cartVersion` + warnings ; l'UI l'INSÈRE dans le composer (jamais d'envoi auto) via `ComposerInsertProvider`.
- **Permissions** : `carts.read/create/update/abandon`, `checkout.read/update/confirm` (AGENT : parcours complet — c'est son métier), `stockReservations.read` (diagnostic, +MANAGER), `stockReservations.manage` (OWNER/ADMIN, aucune route ne l'utilise encore).
- **Audit** : 12 événements `CART_*/CHECKOUT_*/STOCK_*` écrits dans la transaction métier.
- **Frontend** : panneau droit de l'inbox en onglets **Contact / Panier** (`tab-contact`/`tab-cart`) ; `CartPanel` (lignes ± quantité, compte à rebours de réservation, alertes de revalidation avec acceptation de prix, totaux TOUJOURS serveur — chaque mutation remplace le cache par la réponse, rollback = invalidate ; 409 → toast + refetch), `CheckoutForm` (DELIVERY/PICKUP conditionnels, préférence de paiement, save/confirm/cancel, état confirmé figé), sélecteur produit réutilisé en mode `onPickVariant` (« Ajouter au panier »), résumé inséré dans le composer. - **Tests** : e2e `test/carts.e2e-spec.ts` (29 scénarios : cycle de vie, idempotence, 409, revalidation, réservations avec mouvements delta=0, concurrence dernier article, historique multi-réservations + index partiel par SQL direct, expiration par SWEEP WORKER RÉEL, isolation, invariants PostgreSQL finaux), Playwright `e2e/cart.spec.ts` (9 scénarios avec worker réel : picker → panier, totaux, résumé sans envoi auto, prix modifié, checkout DELIVERY confirmé, temps réel deux agents, annulation, bascule de Shop).

## Module Commandes (implémenté — Order + OrderItem + consommation de stock + historique de statuts)

- **Modèles** : `Order` (une seule par `cartId` ET par `checkoutSessionId`, `@@unique([organizationId, orderNumber])`, FK composites chaînées vers shop/contact/conversation/cart en `NoAction` — supprimer une de ces entités ne doit JAMAIS emporter une Order), `OrderItem` (**snapshot définitif** : `productId`/`variantId` en FK simple-colonne `SetNull` — une suppression physique du Product/Variant en test/dev met la référence à null SANS toucher `shopId` ni les champs snapshot, testé par SQL direct ; `productTypeSnapshot`/`trackInventorySnapshot`/`allowBackorderSnapshot` + `stockConsumedQuantity`/`backorderedQuantity`/`stockRestoredQuantity` pour tracer la consommation réelle, CHECK SQL `stockConsumedQuantity + backorderedQuantity = quantity` si suivi), `OrderSequence` (compteur transactionnel par `(shopId, year)`), `OrderStatusHistory` (immuable, `changeType` ORDER_STATUS/PAYMENT_STATUS/FULFILLMENT_STATUS/MULTIPLE), `OrderNote` (append-only, jamais envoyée au client), `OrderMutation` (idempotence dédiée `@@unique([orderId, clientMutationId])` — distincte de `CartMutation`).
- **Le `confirmationSnapshot` du CheckoutSession est l'UNIQUE source d'entrée de la conversion** — jamais le frontend, jamais le catalogue courant, même après modification/suppression du produit. Enrichi (au-delà de la Phase Panier) avec `checkoutSessionId`, `cartVersion`, `checkoutVersion`, et par ligne : `imageUrl`, `compareAtPriceMinor`, `productType`, `trackInventory`, `allowBackorder` — gelés au moment de la confirmation. Parse DÉFENSIF (`order-snapshot.ts`) : un snapshot antérieur à cet enrichissement (champs manquants) est explicitement REFUSÉ (`ORDER_SNAPSHOT_INVALID`), jamais de fallback vers CartItem ou ProductVariant.
- **Numéro de commande** (`PREFIX-YYYY-NNNNNN`) : préfixe STABLE stocké sur `Shop.orderNumberPrefix`, généré une seule fois (candidat dérivé du slug, unicifié par suffixe numérique si collision) et JAMAIS régénéré si le slug change ensuite ; unicité insensible à la casse par organisation (index fonctionnel SQL `shops_order_number_prefix_ci_per_org`). Séquence par `(Shop, année)` : `INSERT … ON CONFLICT (shopId, year) DO UPDATE SET lastValue = lastValue + 1 RETURNING`, DANS la transaction de conversion — un rollback annule l'incrément (compteur transactionnel, pas une séquence `nextval()` : aucun trou lié à un rollback). ⚠️ **Piège réel corrigé** : la pose du préfixe retente sur P2002 (collision de candidat) — sans `SAVEPOINT`, cette erreur AVORTE toute la transaction PostgreSQL et la requête suivante échoue avec « current transaction is aborted » au lieu d'un P2002 exploitable ; `ensurePrefix` pose un `SAVEPOINT` avant chaque tentative et fait `ROLLBACK TO SAVEPOINT` sur échec.
- **Conversion atomique** (`OrderConversionService`) : verrous Cart+CheckoutSession (même ordre que `CheckoutService`, anti-deadlock) → `claimMutation` (réutilise `CartMutation`, existant) → vérifications (CONFIRMED, snapshot présent, cart CHECKOUT_STARTED, versions, IDs cohérents) → pour chaque ligne suivie : réservation ACTIVE non expirée de quantité EXACTE exigée (`ORDER_RESERVATION_MISSING/EXPIRED/MISMATCH`) → numéro généré → Order + OrderItems créés (100 % snapshot) → consommation stock → réservations → CONSUMED → Cart → CONVERTED → `OrderStatusHistory` initiale (SYSTEM) → audit. Idempotence structurelle (`cartId`/`checkoutSessionId` uniques) + réponse 200 (au lieu de 201) si déjà convertie.
- **Consommation backorder-aware** (`OrderStockService.consume`) : `UPDATE inventory_items SET onHand = onHand − LEAST(quantité, onHand), reserved = reserved − quantité WHERE reserved >= quantité RETURNING` — `quantityOnHand` ne devient JAMAIS négatif, le surplus devient `backorderedQuantity` ; mouvement `SALE` avec `quantityDelta` = SEULEMENT la quantité réellement sortie du stock (peut être 0 si tout est backorder). Produit non suivi (`trackInventory=false` au SNAPSHOT) : aucune réservation attendue, aucun mouvement, ligne créée quand même.
- **Statuts séparés** : `OrderStatus` (CONFIRMED→PROCESSING→READY→SHIPPED/DELIVERED→CANCELLED, table `ORDER_STATUS_TRANSITIONS` dans `@whauto/shared` — READY→DELIVERED réservé PICKUP, READY→SHIPPED réservé DELIVERY, SHIPPED→CANCELLED refusé), `OrderPaymentStatus` (mapping initial figé CASH_ON_DELIVERY/PAY_IN_STORE/UNDECIDED→UNPAID, MOBILE_MONEY/CARD→PENDING, **aucune route de modification** dans cette phase), `OrderFulfillmentStatus` (dérivé automatiquement par transition, NOT_REQUIRED déterminé depuis les `productTypeSnapshot` du SNAPSHOT si TOUTES les lignes SERVICE/DIGITAL — jamais depuis le catalogue courant). Toute écriture de statut passe par `OrderTransitionService` (aucune ailleurs).
- **Annulation** (`OrderTransitionService.cancel`) : éligible CONFIRMED/PROCESSING/READY uniquement (SHIPPED/DELIVERED refusés — workflow retour hors scope) ; transition conditionnelle `updateMany` GATE toute la restitution (double annulation = la seconde échoue proprement, jamais de double restitution) ; restitution basée sur `stockConsumedQuantity` HISTORIQUE de l'OrderItem (jamais `trackInventory` courant) ; `InventoryItem` requis absent → `ORDER_STOCK_RESTORATION_FAILED`, rollback COMPLET de l'annulation (jamais de restitution silencieuse à zéro).
- **Idempotence post-conversion** : `OrderMutation` dédiée (`orderId`, `clientMutationId`, `type`, `resultVersion`) pour statut/annulation/note — jamais `CartMutation` réutilisée après la conversion.
- **Permissions** : `orders.read/create/updateStatus/addNote/viewHistory` (AGENT inclus — conversion + statuts opérationnels + notes, c'est son métier), `orders.cancel` (MANAGER+, PAS l'AGENT), `orders.viewCost`/`orders.export` réservées (aucun coût snapshotté dans cette phase, export non implémenté).
- **Audit** : 6 événements `ORDER_*` dans la transaction métier ; l'historique détaillé vit dans `OrderStatusHistory` (pas de duplication).
- **Frontend** : `/orders` (liste paginée, filtres avant pagination, recherche numéro/client/téléphone, **3 badges distincts** commande/paiement/livraison — jamais fusionnés), `/orders/[orderId]` (articles = snapshots affichés tels quels, timeline depuis l'historique, actions de transition, annulation avec confirmation, notes chronologiques, bandeau « paiement à encaisser »). Refresh coordonné : single-flight local + verrou Web Locks `whauto-auth-refresh` + BroadcastChannel `whauto-auth` (`AUTH_TOKEN_UPDATED`/`AUTH_LOGGED_OUT`, fallback documenté) — un seul onglet appelle `/auth/refresh`, indispensable avec la rotation. Refresh préventif à exp−60 s (claim `exp` décodé uniquement pour la planification) ; le 401 (replay unique) reste le secours. **Aucun SSR authentifié** : les Server Components sont des coquilles, les données passent par TanStack Query côté client.
- **Sécurité front** : `getSafeInternalPath` sur tout paramètre `next` (chemins internes uniquement) ; tokens d'URL (verify/reset/invitation) gardés en mémoire et retirés via `router.replace`, jamais loggés ; `getErrorMessage` n'affiche JAMAIS un message 5xx brut (message public + `requestId`) — le `code` d'`ApiError` pilote le comportement.
- **Organization active** : préférence UI en localStorage (`whauto:active-org`), toujours revalidée contre `GET /organizations` ; aucune sécurité n'en dépend. Changement d'org : `key={orgId}` remonte l'arbre (dialogues fermés, sélections réinitialisées, zéro flash inter-tenant). Permissions UI = champ `permissions` de `GET /organizations/:id` (jamais de matrice recopiée), `usePermissions`/`<Can>`.
- **Env** : `apps/web/.env` (Next ne lit PAS le `.env` racine) — `NEXT_PUBLIC_API_URL` = URL complète AVEC `/api`, validée par Zod (`lib/env.ts`), jamais re-suffixée par le client.
- **Tests** : Vitest+RTL (`src/**/*.test.*`, mocks fetch manuels, pas de MSW) ; Playwright (`e2e/`, Chromium, port **3001** dédié, `reuseExistingServer: false` — un autre dev server occupe souvent le 3000 sur ce poste) contre la vraie API en env de test (Redis DB 1, limites hautes) et le **build de production** du front (`next build` requis avant `test:e2e` — le mode dev rebuild en continu et avorte les navigations RSC).
- **Piège Radix** : un `Button asChild` doit passer UN unique enfant au Slot — le spinner `loading` n'existe que pour les `<button>` natifs.
- **Contrainte prod** : cookie refresh SameSite=Strict host-only → app et API doivent partager le même domaine enregistrable (ex. `app.whauto.ai` / `api.whauto.ai`).

Aucune variable IA/Gemini active (sous-phases B/C non commencées).

**Procédure de test Meta RÉEL (manuelle, jamais automatisée — sous-phase A)** : (1) renseigner les vrais secrets Meta dans `.env` (pas `.env.example`) ; (2) exposer l'API publiquement (ngrok/tunnel) et configurer l'URL de webhook + le verify token dans l'App Meta ; (3) `POST …/whatsapp-channel/meta/connect` pour lier la Shop de test ; (4) `GET …/meta/health` (aucun envoi) ; (5) depuis un numéro WhatsApp autorisé, envoyer « Bonjour » au numéro Meta → vérifier la conversation dans l'inbox ; (6) répondre depuis Whauto AI → vérifier la réception côté client + la progression SENT/DELIVERED/READ. Ne jamais lancer un envoi réel sans confirmation explicite.

Le CLI Prisma cherche son `.env` relatif à `packages/database`, pas à la racine — un `packages/database/.env` contenant uniquement `DATABASE_URL` est donc nécessaire en plus du `.env` racine (non commité, à recréer localement).

PostgreSQL Docker est mappé sur le port **5433** (pas 5432) : un PostgreSQL natif Windows occupe fréquemment le 5432 sur ce poste, ce qui provoque un échec d'authentification silencieux si Prisma se connecte au mauvais serveur.
